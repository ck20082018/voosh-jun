# Совместная разработка двух человек

`main` — общая проверенная версия. Каждая задача имеет временную ветку `visual/<задача>` или `logic/<задача>` и Pull Request (PR) в main. После объединения удаляем завершённую ветку. Следующую задачу начинаем от актуальной main. Не держим две постоянно расходящиеся ветки оформления и логики.

## Кто где работает

Друг отвечает за CSS платформы и редактора (`src/editor.css`, `src/runtime.css`, `src/ui/*.css`, `src/screens/*.css`), `src/classic.css`, `src/presentation/**`, `src/ui/Icon.tsx`, геометрию сцены (`src/scene/environment.ts`, `iso.ts`, `objects.ts`, `scene.css`) и будущие `public/assets/**`. Автор отвечает за ядро, сценарии, ноды, каталог, планирование, сохранения, `src/platform/**` и соответствующие тесты. Полный список — в [AGENTS.md](../AGENTS.md).

React-интерфейсы App, Editor, GraphEditor, ConnectionBuilder, экраны `src/screens/*.tsx`, `src/ui/primitives.tsx`, `src/ui/motion.ts`, адаптер Workshop, `src/scene/WorkshopScene.ts`, `src/scene/model.ts`, точки входа, исходная сцена classic, интеграционные UI-тесты, зависимости, конфигурация и документация общие. Перед параллельной правкой общего файла договоритесь, кто меняет какую часть; перечислите изменения в PR. Границы — правила команды, не ограничение доступа. Подробности в [AGENTS.md](../AGENTS.md) и [инструкциях отрисовки](../src/presentation/AGENTS.md).

## Как передавать задачи между логикой и дизайном

Сначала сформулируйте один пользовательский результат и критерии проверки со ссылкой на пакет [MVP](MVP.md). Затем укажите исполнителя, ветку, общие файлы и ожидаемые данные интерфейса. Например: логика предоставляет причину несовпадения материала, оформление показывает ожидаемый и фактический материал, оба проверяют правильную деталь и ошибочную попытку.

До параллельной работы согласуйте состояния, которые затрагивает задача: ожидание ввода, обработка, ошибка, успех, повторная попытка. Передайте пример данных и разрешённых действий. Изменения API, ID и сохранений не входят в чисто визуальную задачу автоматически.

Один участник ведёт изменение общего файла на время задачи; второй может проверить его или работать с независимыми файлами. Если двум задачам требуется одна и та же часть общего файла, сначала объедините меньший PR, затем обновите вторую ветку из `origin/main`. После объединения чужого PR обновляйте свои активные ветки перед следующей связанной правкой.

Для нового экрана сначала подключите минимальный рабочий сценарий к актуальной модели, затем улучшайте оформление небольшими PR. Существующие состояния и команды должны оставаться доступными. Не заменяйте рабочую модель старой копией ради переноса дизайна.

## Одновременная работа на одном компьютере

Используйте отдельную папку Git worktree для каждой задачи. У них общая история Git, но независимые файлы и ветки. На разных компьютерах достаточно отдельных клонов.

После завершения приёмки интеграции и её объединения в `main` создавайте новые рабочие папки из корня репозитория. Имена ниже — примеры для конкретных задач:

```sh
git fetch origin
git worktree add -b visual/workshop-labels .worktrees/visual-workshop-labels origin/main
git worktree add -b logic/result-feedback .worktrees/logic-result-feedback origin/main
```

Откройте каждую папку в отдельной сессии Codex или редактора. Не выполняйте обе задачи из корневой папки. `.worktrees/` исключена из Git и контекста Docker.

В каждой рабочей папке отдельно выполните `npm ci`. Для одновременного запуска Vite используйте разные порты:

```sh
# В папке задачи оформления:
npm run dev -- --port 5174 --strictPort
# В папке задачи логики:
npm run dev -- --port 5175 --strictPort
```

Для Docker указывайте разные имена проектов и порты, выполняя команды из соответствующих рабочих папок:

```sh
# В папке задачи оформления:
DEMO_PORT=8082 docker compose -p voosh-visual up --build -d
# В папке задачи логики:
DEMO_PORT=8083 docker compose -p voosh-logic up --build -d
```

Порт 8081 остаётся для общей проверяемой сборки. Перед браузерной проверкой запишите ветку, коммит и URL: соседний контейнер может показывать другую версию. Одно имя Docker-проекта закрепляйте за одной активной рабочей папкой.

После объединения задачи остановите её dev-сервер или Docker-проект, проверьте отсутствие незакоммиченных файлов и удалите только завершённую рабочую папку из корня репозитория:

```sh
git worktree remove .worktrees/visual-workshop-labels
git fetch origin
git branch -d visual/workshop-labels
```

Не применяйте принудительное удаление папки с незавершённой работой.

## Слова Git

- **clone** — получить репозиторий с историей на свой компьютер.
- **branch** — отдельная линия работы над задачей.
- **commit** — сохранить выбранные изменения в локальную историю с пояснением.
- **push** — отправить локальные коммиты на GitHub.
- **pull** — получить и включить новые коммиты удалённой ветки.
- **Pull Request** — предложение объединить ветку; другой человек читает diff, CI проверяет код, затем разрешённый участник объединяет изменения.

Владелец открывает GitHub → репозиторий → Settings → Collaborators → Add people, вводит настоящий GitHub-логин друга. Друг принимает приглашение. Никто не приглашён автоматически. [Инструкция GitHub](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration/inviting-collaborators-to-a-personal-repository).

Установите Git и Docker Desktop либо Node.js 26. Для приватного репозитория используйте свой вход в GitHub; пароль аккаунта для HTTPS Git не подходит — используйте credential manager/токен или настроенный SSH. Не храните токены в проекте.

```sh
git clone https://github.com/ck20082018/voosh-jun.git
cd voosh-jun
docker compose up --build -d
```

Откройте http://localhost:8081. Для быстрой локальной разработки:

```sh
npm ci
npm run dev
```

Docker пересобирают после изменения исходников; Vite обновляет страницу автоматически. Полные инструкции и создание уровней — в [README](../README.md).

## Начать задачу

Сначала `git status`: если есть незавершённая работа, сохраните её в своей ветке отдельным коммитом, не стирайте её. Следующие команды предполагают чистое рабочее дерево:

```sh
git switch main
git pull --ff-only origin main
git switch -c visual/workshop-colors
```

Для логики вместо последней команды: `git switch -c logic/new-scenario`. Названия задач выбирайте разные. Если pull сообщает о расхождении, остановитесь и разберите историю вместе; не сбрасывайте чужие коммиты.

## Проверить и отправить

```sh
git status
git diff
npm test
npm run build
# Пример: добавляем только файлы своей задачи:
git add src/scene/objects.ts src/scene/scene.css
git diff --cached
git commit -m "visual: improve workshop colors"
git push -u origin visual/workshop-colors
```

Для другой задачи замените пути и имя ветки. `git diff` показывает ещё не добавленные изменения; `git diff --cached` — содержимое будущего коммита. Не используйте `git add .` без просмотра списка. Исправьте проваленные проверки перед PR.

На GitHub откройте Pull requests → New pull request. Выберите base: `main`, compare: свою ветку. Посмотрите Files changed, нажмите Create pull request. Опишите проблему, изменения общих файлов и реально выполненные проверки. Попросите коллегу посмотреть PR. После успешного CI и проверки объедините через Merge pull request; нажмите Delete branch. На компьютере с чистым рабочим деревом:

```sh
git switch main
git pull --ff-only origin main
git branch -d visual/workshop-colors
```

Используйте [шаблон PR](../.github/PULL_REQUEST_TEMPLATE.md). Для изменений поведения и оформления выполните затронутые сценарии [браузерной приёмки](BROWSER_ACCEPTANCE.md), укажите браузер, коммит и результат. Тесты jsdom, успешная сборка и HTTP 200 не подтверждают внешний вид и работу мышью. Если браузер недоступен, оставьте PR черновиком и явно укажите оставшиеся проверки. Владелец может выполнить их вручную на том же коммите и передать результат.

До объединения текущей интеграции исправления приёмки вносятся в её ветку. Новые независимые задачи логики и оформления начинаются от `main` после принятия интеграции. Долгоживущие исходные ветки не используйте как основу для следующей задачи.

## Получить новые изменения во время задачи

Находясь в своей рабочей ветке с чистым деревом:

```sh
git fetch origin
git merge origin/main
npm test
npm run build
git push
```

Это включает изменения коллеги в текущую задачу без переписывания истории. Force push не нужен.

При конфликте `git status` перечислит файлы. Откройте каждый: блоки `<<<<<<<`, `=======`, `>>>>>>>` показывают версии. Разберитесь в обеих правках и вручную составьте правильный результат; не выбирайте одну сторону сразу для всех файлов. Удалите маркеры, проверьте поведение и завершите merge:

```sh
git add src/Workshop.tsx
# Добавьте также остальные разрешённые конфликтные файлы.
git diff --cached
npm test
npm run build
git commit
git push
```

Если ещё не готовы разбирать конфликт, отмените только незавершённое объединение: `git merge --abort`. Поэтому перед merge нужно чистое дерево. Если проверка после merge провалилась, исправьте причину до отправки.

## CI и защита main

Workflow `.github/workflows/ci.yml` запускается для PR в main и push в main: Node.js 26, `npm ci`, `npm test`, `npm run build`. Права только чтения содержимого. Сборка включает проверку TypeScript.

Защита main этой подготовкой **не включается**. После первого успешного CI владелец открывает Settings → Branches → Add branch protection rule, шаблон `main`. Включите Require a pull request before merging и Require status checks to pass before merging, выберите появившуюся проверку `tests-and-build`. Для двух человек можно потребовать одно одобрение. При желании потребуйте обновление ветки перед объединением; не разрешайте force push или удаление main. Сохраните правило. Доступность защиты приватного репозитория зависит от плана GitHub. [Настройка правила](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/managing-a-branch-protection-rule).
